Findings

  • Yes, it is doable, and it takes two changes, not one. The async merge alone (timescale_async_merge) lets the driver push the next file while the previous one merges: driver-observed ingest went from 145k to 177k rows/s (1.22×, 100 files in 5.8 min instead of 7.1). But the request loop stayed blocked (a /health call still took 3.2 s instead of 4.1 s) because the arrow route runs the store call on the event loop and, with the merge queue full, that call now blocks in the queue's back-pressure wait instead of in the merge. Moving the store call to the threadpool (asyncio.to_thread in /insert_timeseries_arrow, the way the JSON insert route already works) frees the loop: /health p50 2 ms in both threaded runs.
  • Reads during ingest. With the threaded route but the synchronous merge, a read on the timeseries store waits for the merge on the shared connection: p90 4.5 s, 80 of 175 reads over 1 s. With the threaded route and the async merge the read only shares the connection with the COPY: p90 138 ms, p99 472 ms, none over 1 s. That is the "everyone else does not wait for it" behaviour the change was for.
  • The gain for the driver is bounded by the merge. The worker merges at 3.4 s per file (3.4 µs/row for these 615k-row files), and the driver's own work per file (read, melt, Arrow, COPY) is about 0.9 s, so the overlap buys ~20% and the queue is full most of the time. Ingest throughput is still the single merge backend's; making that faster (see the plain-insert trace: 3.1× with no ON CONFLICT and a non-unique index) is a separate lever, and the two combine.
  • Data integrity checks passed in all four runs: 61,499,352 rows pushed and 61,499,352 in the hypertable, no staged batch table left behind, the last batch merged 2 s after the driver's last file, no errors in the server log. The 105 store tests, including the seven new async-merge tests (ordering, cross-batch dedupe, drain on close, crash recovery, explicit transactions, sync path unchanged), pass on the VM.
  • Semantics that change with async_merge on: a write's 200 means "durably staged in Postgres", not "merged"; reads see the batch a few seconds later (flush() waits if a caller needs read-your-writes); a Postgres crash loses batches that were staged but not yet merged (UNLOGGED tables, at most the queue depth), whereas a server crash loses nothing because leftover batch tables are merged at the next start. Default is off.
  • Probe caveat. The 1-day read probe returned an empty stream in every run: in the first two because the URI was not a registered point, in the threaded runs because the window was wrong: the file names carry export dates, and the earliest timestamp in the data is 2024-08-20 14:03 UTC, four days after the probe window. It still went through the manager and the store's lookup on the shared connection, which is the wait being measured; the numbers say how long a small read waits, not how long a large scan takes.
