Findings

  • Dropping ON CONFLICT and the unique constraint doubles ingest. All 1000 files (682.6M rows) merged in 36.2 min at 314k rows/s. On the 670 files the baseline managed in its 50-minute cap, this variant took 25.1 min against 50.0 min: 2.0× end to end. The acquirium end-to-end run of this branch took 77.4 min for the same 1000 files.
  • The merge statement itself is 3.1× cheaper: 1.79 µs/row against 5.49 µs/row on the same 452M rows. EXPLAIN on the same file (737k rows) shows why: 4.0 shared-buffer hits per row instead of 8.0, and 2 WAL records per row instead of 3. The ON CONFLICT arbiter probe (a full b-tree descent on the unique index before every insert, plus the speculative-insertion token in WAL) was half the work of the Insert node. The remaining cost is the heap insert plus one b-tree insert into the non-unique index, still on CPU in a single backend (91% of samples on CPU; WAL-write waits appeared at 4% now that the backend generates WAL faster than the wal writer drains it).
  • The merge is no longer alone at the top. Of the 36.2 min: merge 54%, COPY into the staging table 24%, everything Python-side 17%. The Sort feeding the insert (external merge on disk, work_mem 16 MB) is now 29% of the statement (0.32 s of 1.12 s on the 737k-row file), so work_mem and the staging COPY are the next things worth looking at, not the Python code.
  • Cost stays flat with table size (1.60 µs/row over the first 100 files, 1.63 over the last 100, 36 GB heap + 22 GB index at the end, 101 chunks). The two plateaus at ~4 µs/row in the chart (83 files, around files 207–300 and 940–968) are host noise, not the index: during those files the CSV read, the melt and the COPY slowed by the same 2.5–3× while the backend stayed on CPU and the container's CPU share did not change, which is the VM getting fewer cycles from the shared host. Outside them the merge runs at 1.43 µs/row, 3.8× the baseline; the 2.0× end-to-end figure includes that noise, so it is a conservative number. The index is the same size as the unique one; uniqueness costs nothing on disk, only per-row CPU on the write.
  • Correctness caveat: the constraint was doing work. The variant stored 682,580,597 rows; acquirium and the unique-index run stored 682,522,976 for the same files. The 57,621 extra rows (0.008%) are (ref_id, ts) pairs that occur in more than one CSV: consecutive DPR exports overlap by a few minutes. The Python dedupe in _prepare_frame only removes duplicates within one batch; cross-file duplicates were absorbed by ON CONFLICT DO UPDATE and are now stored twice. Any read that assumes one row per (stream, ts) would see them. Keeping the write path this fast while still enforcing uniqueness means deduplicating against the table cheaply, for example an anti-join on the batch's time range before the insert, or accepting duplicates and deduplicating on read.
  • WAL and checkpoints: 99 GB of WAL (158 B/row), 193 requested checkpoints in 36 min with max_wal_size = 1 GB; the checkpointer wrote continuously. Same side cost as the baseline, now proportionally bigger because the merge got cheaper.
