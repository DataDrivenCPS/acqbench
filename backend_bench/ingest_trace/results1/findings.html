Findings

  • The time is inside one Postgres statement. INSERT INTO timeseries … SELECT … FROM staging JOIN ref_ids … ORDER BY ref_id, ts ON CONFLICT (ref_id, ts) DO UPDATE takes 82.8% of every file (5.5 µs/row, 41.4 min of 50). COPY into the TEMP staging table is 9.3% (0.6 µs/row). Everything that runs in Python (reading the CSV, parsing timestamps, unpivot, register_declared, Arrow IPC both ways, the manager's per-stream value_kind SELECTs, split/dedupe, write_csv) adds up to 6.1%. Same order of magnitude as the acquirium run: this replay merges at 150.6k rows/s, acquirium end to end at 147k rows/s.
  • It is CPU, in a single backend. In 99.1% of the 12,406 wait-event samples taken during the merge the backend had no wait event (on CPU); I/O waits were 0.8% (DataFileExtend, DataFileRead, temp file for the sort) and WAL lock waits 0.04%. The Postgres container used 0.97 of 4 cores for the whole run; the tracer process 0.13. Three cores sat idle because one INSERT statement is one process.
  • What the backend is doing per row (EXPLAIN ANALYZE, file 650, 737k rows, 4.07 s): the Hash Join + Sort that feed the insert take 0.33 s (8%); the Insert on timeseries node takes the remaining 92%. Per row it performs ~8 shared-buffer accesses (5.9M hits), writes 3 WAL records (2.2M records, 200 B/row: heap tuple, unique-index tuple, and the chunk's insert), and dirties a heap page and an index page. That is the ON CONFLICT arbiter probe on idx_timeseries_ref_ts_unique plus the heap insert plus the b-tree insert, ~5.5 µs of CPU per row.
  • It does not degrade with table size. Merge cost was 5.52 µs/row over the first 100 files and 5.67 µs/row over the last 100, with 452M rows (24 GB heap + 14 GB index, 76 chunks) in the hypertable at the end. The sorted input keeps the index inserts sequential per stream, so the b-tree working set stays in shared_buffers (backend reads: 2,858 blocks in 50 minutes).
  • WAL and checkpoints are a side cost, not the bottleneck. 92 GB of WAL for 452M rows (~30 MB/s). With max_wal_size = 1 GB (timescaledb-tune default) that forces a checkpoint every 18 s: 168 checkpoints, all "requested", 5.2M buffers (39 GB) written by the checkpointer, which was writing for 2,680 of the 3,000 s. The checkpointer is a separate process and the backend never waited on it (no CheckpointWriteDelay or fsync waits on the backend), so this costs disk bandwidth and a second core, not merge time. It would matter on a slower disk.
  • The sort spills (work_mem = 16 MB, external merge on 14–24 MB of temp), but the whole Sort is 8% of the statement; raising work_mem would save ~0.3 s per file at most.
  • Projection. At 150.6k rows/s the full 1000-file set (682.5M rows) is 75.5 min; the acquirium run measured 77.4 min. The Python side of the pipeline (6%) is not where a speed-up will come from; the merge is bounded by per-row b-tree + heap + WAL work in one process.
