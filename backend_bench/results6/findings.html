PR 91 update (54ca661, COPY into a TEMP staging table). Against the same 13:41 main baseline as the previous fix-1 run, this commit leaves the numbers where 4267175 put them: ingest 17.2 min / 132k rows/s (previous fix-1: 16.9 min / 135k — a 2% difference, inside run-to-run noise), 12.81 GB on disk (identical schema, identical bytes), Postgres at 0.93 cores with acquirium at 0.15. Queries are all in the 0.67–1.13× band against main (median 0.84×, vs 0.92× for the previous fix-1 measured an hour closer to that baseline); the commit does not touch the read path, so that spread is host noise, and the LIMIT shapes stay at 1.5–2.7 ms.

Why no ingest gain: the CSV driver feeds the server through bulk_insert_polars, which on 4267175 already staged the batch server-side (ADBC ingest into a real staging table) and merged it with one INSERT … SELECT … ON CONFLICT. 54ca661 swaps ADBC for a CSV COPY into a TEMP table on the same connection and routes upsert_rows/replace_rows through the same path. The cost this workload pays is the Postgres-side merge into the hypertable's unique index, which is unchanged, so throughput is unchanged. The commit's wins are structural — one write path, atomic replace, no ADBC dependency — and its throughput effect would show on the per-call upsert_rows API (the old executemany loop), which the driver bulk path never used. fix-2 got its extra 1.3× on this same merge step by replacing ON CONFLICT with delete-then-insert.
Verdict (4267175, before PR 91's last commit). The updated ums-timescale-fix (4267175: psycopg path kept, hypertable re-keyed by integer ref_id, one unique index) reaches the same footprint as fix-2 (12.8 GB, 94 B/row, 7.2 GB table + 5.6 GB index — identical schema on disk) and gets 1.77× ingest against its same-day main (29.9 → 16.9 min, 76k → 135k rows/s), while no read regresses: median query p50 0.92× main, every one of the 30 queries between 0.77× and 1.17×, with the ≥ 60k-row scans 8–10% faster and cold first-touch reads ~25% faster on the big streams. The latest N / LIMIT shapes stay at ~2 ms, exactly where main has them.

The ingest gain from old to new fix-1 (1.44× → 1.77×) is what the narrower rows and the 5× smaller unique index buy on the unchanged psycopg upsert path; Postgres is still the single ~0.9-core bottleneck with acquirium idle at 0.14 cores. fix-2's further step to 2.30× comes from moving the staging work into the acquirium process (0.75 cores) and replacing ON CONFLICT with delete-then-insert — but that is also what costs it the LIMIT pushdown and adds a ~4 ms floor to point reads.
Recommendation. PR 91 as it stands (fix-1 with the COPY path) is the safe merge: it captures all of the disk win and most of the ingest win with zero read-side risk. fix-2 is only worth its read-path regressions if large-scan latency matters more than latest-value reads — and if its LIMIT handling is fixed (push ORDER BY ts … LIMIT n into the Postgres SQL via postgres_query()) it would dominate on everything except the ≤ 400-row point reads, where the ~4 ms DuckDB-attach floor remains.
Comparability. Each variant ran immediately after a fresh run of the same main commit on the same day (09-02 for old fix-1, 09-04 for fix-2 and, in a later campaign, new fix-1). main's ingest and disk reproduced exactly on all three days (30.4/30.4/29.9 min, 66.47 GB), but its large-scan latencies varied 384–484 ms with host load, so raw milliseconds are not comparable across columns — the "÷ main" ratios are. The duckdb column is main's duckdb backend from 09-04 (unchanged by any of these branches), for scale.
