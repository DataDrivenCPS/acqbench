Setup. Both backends run the same acquirium commit, ums-timescale-fix @ d6b6e1a (PR 91 head), on the same 4 vCPU / 16 GiB cgroup, against 1000 DPR CSVs (the 200 from the earlier campaigns plus 800 more chosen evenly across 2024-08 → 2026-08): 682.6M rows pushed, 682,522,976 stored on both, 292 streams. The 50-query set was generated on the duckdb run (absolute timestamps anchored at 2026-08-30) and replayed unchanged on timescale. Queries 31–50 are new for this dataset: 1-year / 180-day windows, deep-history windows a year back, a third numeric stream, the sparsest numeric stream (29k rows), a second text stream, LIMIT inside long ranges, and two batch-stats calls through POST /timeseries_info.
Ingest. DuckDB 19.9 min / 572k rows/s vs Timescale 77.4 min / 147k rows/s — DuckDB 3.9× faster, and both rates are flat across the 5× larger dataset (200 files: 586k / 148k). DuckDB uses 1.5 cores in the acquirium process; Timescale keeps Postgres at 0.93 cores with acquirium at 0.17, i.e. it is still bound by the single-threaded staging→hypertable merge (731 of 1121 sampled Postgres statements were the INSERT … SELECT … ON CONFLICT, 91 the COPY).
Footprint. DuckDB 36.5 GB (53.5 B/row) vs Timescale 57.8 GB (84.6 B/row): 35.9 GB of table plus a 21.8 GB unique (ref_id, ts) index, 101 chunks, none compressed (the 7-day policy never fired within the run). Peak memory: DuckDB server 10.3 GB RSS — 63% of the 16 GiB cgroup, up from 5.5 GB on 200 files; Timescale 4.5 GB server + 9.0 GB Postgres.
Queries — the two backends win different regimes, and the split is sharper at this scale.
  • Large scans (≥ 170k rows, 16 queries): DuckDB 1.3–2.0× faster. 2.76M-row full-stream reads 1.7 s vs 2.7 s; 1-year 0.97 vs 1.43 s; 30-day windows 118 vs 155–235 ms. Text streams are Timescale's worst case (1.9×).
  • Small windows (≤ 6k rows, 14 queries): Timescale 2–5× faster. 1-day 5.5 vs 14 ms, 1-hour 1.9 vs 8 ms. DuckDB's per-read floor has grown from ~4 ms on 200 files to ~8 ms here — the connect-per-read cost now includes a larger catalog and more row groups to prune.
  • LIMIT / latest-N (5 queries): Timescale 2–11× faster. latest 1 5 vs 61 ms, 1-year latest 1000 3 vs 19 ms, 90 days limit 100000 91 vs 335 ms — DuckDB materialises the window before applying LIMIT and that window is now 2.76M rows.
  • Sparse stream (29k rows): Timescale 7.5× faster (29 vs 219 ms). DuckDB has to scan every row group that might contain the stream's ref_id; with 292 streams interleaved in insertion order that is most of the 36 GB file, while Postgres walks 29k index entries.
  • Batch stats over all 112 live streams: Timescale 30× slower (24.6 s vs 0.82 s; 37.8 CPU-s per request). timeseries_info_batch is COUNT(*), MIN(ts), MAX(ts) … GROUP BY ref_id over the whole 682M-row hypertable: Postgres does a full scan (no covering index for count), DuckDB answers from zonemaps and a parallel aggregate. Single-stream stats are close (247 vs 327 ms). Any UI that polls stream stats will feel this.
Median p50 ratio timescale ÷ duckdb over all 50 queries = 0.75, but that number is meaningless on its own — it is the mix of shapes above.
Robustness finding for PR 91 (and the reason this campaign needed a second Timescale run). One of the 1000 files, DPR Pilot R1 SCADA v14.10 - 2026.01.31-2156-46.csv, ends in 1.16 MB of NUL bytes from a truncated write. DuckDB ingested it. On Timescale the branch's COPY path sends text values verbatim, Postgres rejects 0x00 in UTF-8 (invalid byte sequence for encoding "UTF8": 0x00, COPY _acquirium_incoming_timeseries, line 171171), the server returns 400 for the batch, and the driver retries the same file on every tick forever — ingest froze at 652/1000 files (439.7M rows) and the harness abandoned that run after 40 min without progress (kept as results10/*.STALLED.*). A single bad byte wedges the whole Timescale ingest permanently; the store should strip NUL from text values before COPY (or the driver should reject the row) rather than fail the batch. The run reported here used a copy of the file with the NUL tail removed (the only file with NUL or invalid UTF-8 out of 1000; original kept in ~/dpr_1000_orig). Effect on comparability: total rows identical on both backends; one query (#33, P1 full range numeric) returns 2,763,643 rows on Timescale vs 2,763,642 on DuckDB — the truncated last line of that file parsed as one numeric row after sanitising and as a non-numeric one before.
Caveats. Queries 37, 38 and 44 return zero rows on both backends by data, not by design: the two "1 year back" windows land in a gap in the SCADA record and the sparse stream has nothing in its last 30 days; they are kept as cheap empty-window probes. The "cpu ms" column is 100 ms-resolution process accounting. Both runs were back to back on the same host; the run's provenance (GitHub head = clone, module path, Postgres image digest, 0 tables before start, schema after boot, pg_stat_activity samples) is recorded in the JSON.
