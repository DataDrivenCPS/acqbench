Ingest Path: three index choices for the insert_timeseries store

The pipeline behind POST /insert_timeseries, replayed in-process against a throwaway DuckDB with three timeseries-table index configurations: no index, a composite (ref_uri, ts) index, and a low-cardinality (ref_uri) index. Throughput is capped by Python either way (51k vs 46k vs 45k rows/s) — but the two indexes fail differently: the composite pays a constant 12% tax, while (ref_uri) is cheaper per commit yet develops stop-the-world checkpoint stalls that grow with the table — 3.5-minute freezes by 400M rows.

Scaling behaviour

Left: per-file throughput is flat for all three — no per-row degradation to 330–400M rows; the (ref_uri) line collapses at the very end only because four back-to-back checkpoint stalls land there. Right: those stalls are the real difference. (ref_uri, ts) stalled once (25s @ 83M rows) and never again; (ref_uri) stalled at 36–40s around 83M rows and at 183–213s around 395M — stall duration grows roughly linearly with table size (~0.5s per 1M rows), because each checkpoint rewrites huge ART subtrees under its 239 low-cardinality keys. Its final close-checkpoint took another 197s.

Key findings

  • The ingest ceiling is Python, not the index choice. 83–85% of wall time is identical pure-Python row loops in every configuration: prepare_value_columns (46%), insert_timeseries_batch assembly (22%), endpoint regrouping (15%). The three configs differ by at most 13% in throughput. Vectorising the split is worth more than any index decision.
  • The composite (ref_uri, ts) index is the predictable one: a constant 12% throughput tax (all of it at COMMIT, 1.7 s per 1M rows, flat to 330M), one 25s checkpoint stall in 441 files — but the largest footprint at ~45 B/row of index (~178 GB projected).
  • The low-cardinality (ref_uri) index is cheaper per row but degrades catastrophically at checkpoints. Steady-state commit is only 1.1 s/M and storage is ~40% smaller than the composite — but with 239 distinct keys over hundreds of millions of rows, each checkpoint rewrites enormous ART subtrees: stalls went from 36–40s at 83M rows to 183–213s at ~395M (plus a 197s close-checkpoint), roughly linear growth. At full-corpus scale that extrapolates to ~half-hour freezes — unusable for live ingestion.
  • Upsert semantics never depended on an index: DELETE+INSERT dedupe behaves identically in all three configs, and the DELETE anti-join stays at ~60–100ms/file via zone-map pruning even with no index at all.
  • Row accounting closes exactly in all three runs (melted − NaN − dupes = count(*)), and the longest run surfaced a new data-quality find: 643 (NULL, NULL) rows from non-finite (±Inf) values in files after 2023-09-14 — split_value silently nulls non-finite numerics. Together with production’s NaN→"NaN"→(NULL, NULL) behaviour (~1.3% of all cells), the NULL-row handling deserves an upstream fix.

Method. local_ingest_bench/ingest_path_bench.py replays, in one process, the exact main-branch code path behind POST /insert_timeseries: endpoint grouping → Manager.insert_timeseries_batch (per-stream value-kind lookup, per-row assembly into a polars Object frame) → DuckDBStore.bulk_insert_polars (prepare_value_columns, UTC normalise, dedupe, DELETE+INSERT in one transaction), with storage code copied verbatim from git show main:. Driver-side prep mirrors DPRTrailerCSVDriver (header by content, Date + Time → UTC via %m/%d/%Y %I:%M:%S %p, _safe_name, per-stream kind inference, lazy stream registration) but uses pandas for read + melt as specified. Every step is timed for wall, process CPU, and RSS (100 ms sampler). Both index configs keep exactly one CREATE INDEX; UNIQUE(ref_uri, ts) is removed in all three because DuckDB materialises it as an additional ART index. Deviations: no HTTP/JSON/pydantic layer; no RDF-graph writes; pandas drops NaN cells that production stores as (NULL, NULL); Resilio’s .sync archive excluded; runs stopped at ~330–400M rows (the last via --max-rows auto-stop); per-file records in results/full-noindex, results/full-single-index, results/full-ref-only; each DB deleted after its consistency queries. Main’s stock six-index schema was measured earlier and is out of scope here; its calibration data remains in results/calibration.
