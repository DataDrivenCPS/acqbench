1 · Concurrent registration, and what it does to the rest of the API

Each row registers N apps at once from N client threads and starts them keep-alive, while a background probe hits /health and /apps/list every 250 ms. /apps/list takes the app supervisor's record lock; /health takes no lock but shares the same bounded request threadpool — so the two together separate "the lock is held" from "the whole server is gone".

main deadlocks at 50 concurrent registrations. Not "slows down" — stops. None of the 50 requests returned inside the 300 s budget, the probe's /health calls started timing out too, and the server never recovered: it had to be killed. AppSupervisor.register_app holds _lock across ray.get(actor.register), and that actor call re-enters the same server over HTTP. Every sync endpoint runs on one bounded threadpool, so once enough registration requests are parked on the lock there is no thread left to serve the callback the lock-holder is waiting for. This reproduced twice — once during registration, once while deleting 50 apps.
The branch's lock split works. Registration reserves the app name with a placeholder and serializes only the build on a separate _build_lock that no request path takes. The visible effect is dramatic: /apps/list p95 stays between 6.1 and 15.0 ms at every count, versus main's climb to the 60 s probe ceiling by 25 apps.

Serial registration removes contention entirely, so what is left is the per-app cost and whatever the lock blocks anyway.

Even with one registration in flight, main parks /apps/list for seconds — the lock is held for the whole build, not just the dict update. The branch's faster registration is partly the dropped resolve_dependencies pass (main runs an extra resolved_nodes() SPARQL per query at registration; the branch removed depends_on entirely).

New on the branch: most of a 50-way registration storm fails with HTTP 400. The supervisor builds an Acquirium(...) client inside the request handler, and that constructor health-checks the server it is already running in (_wait_for_server, 3 s read timeout, 60 s budget, over localhost). Under 50-way concurrency that self-call times out and registration fails with a misleading ConnectionError: … did not answer /health within 60s … Is the server running?. On a cold server only 16–20 of 50 survive it. The server stays healthy, so this is a bounded failure rather than main's total one — but it is a real regression risk at scale, and the error text points at the wrong thing. Numbers below.

main reproduces exactly. Both repetitions: 0 of 50 returned inside 300 s, both probe endpoints timing out, teardown unable to remove a single app, server dead afterwards. Three observations of the same deadlock now, including the discarded one.

The branch's failure rate is worse than the first pass suggested. On a cold server only 16 and 20 of 50 registrations succeed; the earlier 38/50 came at the end of an escalation, on a server whose Ray workers were already warm from the 1/10/25 counts, so each registration finished well inside the 60 s self-check budget. Cold, the storm is slow enough that the supervisor's own health check gives up. The client-side error is now captured verbatim:

Acquirium server at http://localhost:8811 did not answer /health within 60s (last error: HTTPConnectionPool(host='localhost', port=8811): Read timed out. (read timeout=3.0)). Is the server running? Start it with: acquiri

What makes it self-inflicted: each of the 50 in-flight registrations builds its own Acquirium, which polls /health every 3 s for up to 60 s — so the failing requests generate the very load that starves the endpoint they are waiting on. Note the server itself stays fine throughout: /apps/list p95 is 6.1 ms and all 50 apps tear down in 2.2 s.

Where the polling went. On main every app calls graph_status() on the server once per tick, so the poll rate is the fleet's tick rate: 23.68 req/s for 25 apps at 1 s. The branch floors graph polling at max(interval, 10 s), independent of how fast the app runs: 2.34 req/s. That is a whole request per tick removed from a five-request tick — and it is the request that sat in front of the run on the actor's own thread.

And the tick grid holds. main's loop waits interval after each run finishes, so the period is interval + run time and drifts: p95 2,004 ms against a 1,000 ms request. The branch's IntervalScheduler schedules from the previous deadline, so p95 is 1,021 ms.

main piles up. It dispatched 50 runs for an app that can complete about 12, running up to 7 concurrently and leaving 5 still in flight when the window closed. Nothing bounds this: a slow app on a fast interval keeps spawning Ray tasks. The branch dispatched 10, skipped 51 ticks and counted them, and never had more than 1 run in flight.

run_timeout

Branch only. A deliberately hung run (time.sleep(3600), no cancellation point) with run_timeout=3: recorded 5 timeouts in 20 s and kept skipping ticks (15 skipped) instead of stalling. On main the parameter does not exist: TypeError: Acquirium.run_app() got an unexpected keyword argument 'run_timeout' — a hung run there is unrecoverable short of killing the app.

5 · What this adds up to

  • The branch fixes a server-killing bug. 50 concurrent registrations deadlock main permanently; the branch survives them with the rest of the API answering in single-digit milliseconds. That alone justifies the change.
  • Registration itself is not faster under load. Both refs serialize the build — the branch just moved it to a lock nothing else takes. Registering 25 apps still takes 72 s (main) / 80 s (branch), and per-app p50 grows linearly with N on both. If registration throughput matters, that build lock is the next thing to attack.
  • Steady-state server load drops by the poll rate. One fewer request per app per tick, 10.1× less /graph_version traffic, and app runs come back branch 2.7× faster at p50.
  • Overrun protection is real and cheap. No pile-up, no unbounded Ray task growth, and the skip counter is visible in /apps/list.
  • One new problem to fix before merge: the in-handler Acquirium(...) self-health-check that fails roughly two thirds of a cold 50-way registration storm. It should not health-check the server it runs inside, and it should not reach itself through localhost.

Caveats

  • One laptop, one run per cell, no repetitions — treat 10-20% differences as noise. The findings above are all order-of-magnitude or categorical (dead / not dead).
  • Apps are read-only and trivial (one bound query, ~18 ms of local compute). Nothing here says how a real soft sensor behaves; it isolates runtime overhead, not app work.
  • The registration storm is deliberately hostile — N clients registering simultaneously. Deployments that register apps from a config file at boot hit the serial path instead, where main survives but still blocks /apps/list for seconds per app.
  • 50 apps was the agreed ceiling for this machine; neither ref's actual app-count limit was probed.
  • Teardown of 50 apps also wedged main once (no timeout on the stop/deregister actor calls; the branch bounds them at 10 s and then kills). It is reported here as an observation, not a measured comparison — the harness stops hammering a wedged server rather than characterising it.
