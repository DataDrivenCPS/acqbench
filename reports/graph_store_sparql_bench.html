What actually changed. On main, sparql_query holds the store's RLock across both the Oxigraph call and the row materialization, and any write invalidates the imports-union graph so the next union query re-materializes data + full ontology closure synchronously, on the caller's thread. On graph-store-derived-cache, inference is run by a single-flight background thread and published into a named graph; queries take the lock only for the lazy Oxigraph call and materialize rows outside it, reading the last published view unless wait_for_fresh=True.

Head-of-line blocking the headline

The sweep above runs every reader on the same expensive mix, which hides the difference. This test does not: one thread loops an expensive query (6d1f307f42, ~2,808 ms) while the main thread issues a cheap one (a single bound-predicate lookup, ~0.6 ms alone). Same query, same model, both branches.

On main a cheap query behind one expensive query waits for the expensive query to finish — the global RLock is held across execution and row materialization, so latency goes from sub-millisecond to over two seconds and only 10 cheap queries complete in 20 s. On the branch the same cheap query is unaffected (1.06×) and 30,126 complete. This is the concurrency property the new architecture actually buys.

Queries that never finish

8 of 185 exceeded a 20 s watchdog — on both branches, the same set. They are excluded from the timed comparison above and listed here instead, because a storage change cannot fix them.

The discriminator is a single feature: an unbound-predicate join (?v0 ?p_e0_1 ?v1), where the predicate is a variable rather than a fixed IRI. It costs about 240× on this model, and these 8 are its tail:

All of them are explore "connected within N hops" traversals, compiled as UNION branches of increasing path length with every predicate left as a variable. The fatal branch looks like this — three chained joins, all predicates unbound, with both endpoints constrained only by a subClassOf* type subquery:

{ ?v0 ?p_e0_1 ?x_e0_1 . ?x_e0_1 ?p_e0_2 ?x_e0_2 . ?x_e0_2 ?p_e0_3 ?v1 . }

Over 18,949 triples that is close to a cartesian walk, and the deepest of these go to 8 hops. The NOT IN lists (up to 12 excluded predicates) are the generator pruning structural predicates like s223:cnx after the fact; the join still enumerates everything first, then filters. Four of the eight are byte-for-byte the same query but for one terminal property lookup, so there are really three distinct shapes here. The fix is a bounded predicate alternation in the compiler (?v0 (s223:cnx|s223:connectsTo|…)/… ?v1) rather than a bare ?p at each hop.

A slow query is worse than it looks on main. While probing, a query abandoned at the watchdog on main left every subsequent query in that process timing out too — including trivial ones — because the global RLock is still held by the abandoned query. The probe harness had to restart the process after each timeout to make any progress. That is the same mechanism as the head-of-line result above, in its most extreme form: on main one runaway query takes the whole graph store offline.

Read this one carefully: it is a negative result. Neither branch scales on this workload — throughput is flat near 7–9 q/s from 1 to 16 readers on both, and p50 degrades roughly in proportion to reader count. When every thread runs the same expensive mix, the branch's advantage disappears: Oxigraph query evaluation still happens inside the lock, and what falls outside it (row materialization) is Python, so the GIL serializes it anyway. The derived cache does not make an all-heavy read workload parallel. Its win shows up when queries have different costs — see the head-of-line section above.

The fresh column is the branch running every read with wait_for_fresh=True, i.e. opting out of eventual consistency. With no writer running the cache is already current, so it costs only the extra condition check — it tracks the published numbers closely.

What this adds up to

  • Single-query latency is roughly a wash. Median p50 11.85 ms on main vs 11.56 ms on the branch; the branch is meaningfully ahead only on the expensive queries, where the pre-materialized inferred graph saves re-deriving work.
  • Uniform concurrent reads do not scale on either branch. This is the honest negative result — do not claim concurrency scaling from this workload.
  • Mixed-cost concurrency is where the architecture pays. A cheap query behind an expensive one goes from 3,028× slower to 1.06× — the difference between a graph store that a slow query takes offline and one that keeps serving.
  • Writes no longer stall readers. Under 4 concurrent readers a write costs 2,213 ms on main and 52 ms on the branch, because the closure rebuild moved off the caller's thread.
  • Bad query plans are unchanged. The same 8 queries exceed 20 s on both branches. Those are an explore-builder codegen problem (unbound-predicate joins), not a storage one, and the derived cache does not address them.
  • The corpus is DPR-only, harvested from real runs. Queries against acquirium's driver metadata return 0 rows here because the disposable store has no registered drivers; they are kept because they still exercise the non-dependency code path.
