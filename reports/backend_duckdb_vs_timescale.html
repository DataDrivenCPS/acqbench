What the numbers say

Ingest. DuckDB took the 200 files at 612,457 rows/s (3.7 min), TimescaleDB at 82,773 rows/s (27.6 min) — a 7.40× gap. With Timescale, postgres itself ran at 0.94 cores for the whole ingest while the acquirium process idled at 0.1 cores: the bottleneck is the server-side upsert + 5 index maintenances per row, not the CSV parsing or the HTTP path (which is identical on both runs).
Disk. 7.31 GB vs 66.47 GB. The Timescale hypertable is 13.87 GB of table data and 52.59 GB of indexes — the acquirium schema creates a unique (ref_uri, ts) index plus four partial indexes, and none of the 12 chunks were compressed yet (the compression policy only touches chunks older than 7 days, on its own schedule). That is 486 B/row vs 53 B/row.
Queries. The two backends win different regimes. On the large scans (≥ 60k rows) DuckDB is ~20–30% faster (e.g. 535k rows: 316.59 ms vs 408.39 ms). On point/small-window reads (≤ 10k rows) Timescale is 2–3× faster: it answers in ~1.2–1.5 ms where DuckDB has a ~3 ms floor (a fresh connection per read, see the duckdb-index notes). Two shapes stand out: latest 1 desc (11.97 vs 1.45 ms) and 30 days limit 10000 (116.74 vs 7.76 ms) — DuckDB appears to materialise the whole window before applying LIMIT, postgres stops at the index scan. Both EMPTY queries return 0 rows on both backends in ~1.3–2.5 ms.
Cold reads. The first-ever request against each large stream costs an extra ~200 ms on Timescale (629 ms cold vs 408 ms warm on P1 full range; the smoke run even saw a 7 s first query) as pages come off disk into shared_buffers; DuckDB's cold and warm numbers are within noise.

Ingest

Same code path for both: acquirium server with recreate = true, then the DPR CSV driver (a thin CSVIngestDriver subclass) pushed over HTTP with insert_batch_rows = 50000. Wall time is from driver start returning to the driver's last "inserted N observation(s)" log line. TimescaleDB is timescale/timescaledb:latest-pg17 in a docker container inside the same VM, tuned with TS_TUNE_MEMORY=8GB TS_TUNE_NUM_CPUS=4, default acquirium schema (hypertable on ts, 5 indexes, compression policy after 7 days).
