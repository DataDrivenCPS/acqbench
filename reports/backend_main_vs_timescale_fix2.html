Verdict. ums-timescale-fix-2 (Timescale driven through DuckDB's postgres extension, ref_id-keyed hypertable, delete-then-insert) is a large win on the write side and on every scan ≥ 60k rows, with one real regression on the read side that should be fixed before merge. Ingest 2.3× faster (30.4 → 13.2 min, 75k → 172k rows/s). 5.2× smaller on disk (66.5 → 12.8 GB): the table itself halves (13.9 → 7.2 GB, integer ref_id instead of a text ref_uri per row) and the index bytes drop 52.6 → 5.6 GB (one 4.4 GB unique (ref_id, ts) index plus Timescale's 1.3 GB ts index). Large reads 2.5× faster (P1 full range: 384 → 150 ms; 30-day windows 154 → 64 ms) — Timescale on fix-2 now beats DuckDB itself on the big scans (150 vs 326 ms), and cold first-touch reads fall from ~600 to ~200 ms. The DuckDB backend is unchanged by the branch: 586k rows/s, 7.3 GB, median query ratio 1.00.
Regression: LIMIT / "latest" reads. Every query with a limit now costs a flat ~90 ms on Timescale regardless of how few rows it returns: latest 1 desc 2.0 → 90 ms (44×), latest 100 desc 1.6 → 88 ms (54×), limit 1000 asc 2.4 → 91 ms (38×), 30 days limit 10000 10 → 45 ms (4.5×). The ~90 ms is the cost of pulling the whole 535k-row stream through the postgres scanner: DuckDB pushes the ref_id filter (and, it seems, the ts range — the 30-day+limit case is half the price) into the attached scan, but not ORDER BY ts … LIMIT n, so Postgres streams the full stream and DuckDB sorts and truncates it locally. Main's psycopg path let Postgres stop at the index after n rows. This is the same shape DuckDB's own store already mishandles (native DuckDB: 30 days limit 10000 118 ms, latest 1 16 ms), so both stores would benefit from the fix; for the attached-Postgres case the natural fix is to route LIMIT reads through postgres_query() with the ORDER BY/LIMIT inside the Postgres SQL.
Small reads gain a ~4 ms floor. Reads that return ≤ 400 rows go from ~1.5 ms to ~5.3 ms (P1 1 hour, 10 min, 1 min; the EMPTY-window probe 1.2 → 4.8 ms): each read now costs a DuckDB → attached-Postgres round trip instead of a pooled psycopg cursor. That floor is the same as DuckDB's own ~4–6 ms per-read floor, so it is not a regression relative to the duckdb backend, but it does give up Timescale's former 3× advantage on point reads. Mid-size reads (~8.5k rows, 1-day windows) are unchanged at ~7.5 ms.
Where the write-side cost went. Postgres still runs at ~0.9 cores during ingest, but the acquirium process now does real work too (0.75 cores, staging frames through DuckDB and the binary COPY), so the ingest is no longer a single-core Postgres upsert queue. Per-row work fell because there is one small integer-keyed index to maintain instead of five text-keyed ones and rows are half the width. Still 0 of 12 chunks compressed (7-day policy). Peak RSS is essentially unchanged (server ~3.9 GB, postgres ~6 GB).
Comparability. All four runs were back to back on the same host state (main resolved to the same c09d321 as the 2026-09-02 campaign). main/duckdb reproduced yesterday's numbers to within 1% on ingest, disk, and every query; main/timescale reproduced ingest and disk exactly, but its large-scan latencies were ~20% faster than yesterday (384 vs 484 ms for P1 full), consistent with the host load noise noted before. For reference, yesterday's intermediate ums-timescale-fix (only dropping the partial indexes) gave 1.44× ingest and 1.82× smaller disk with no query change; fix-2 is a further 1.6× on ingest and 2.9× on disk beyond that.
