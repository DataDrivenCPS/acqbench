Query Latency: what each index actually buys

Three identical 100M-row DuckDB stores — no index, (ref_uri), (ref_uri, ts) — measured with main’s two query templates, timeseries_info() and timeseries(). The verdict is sharp: the composite index is never used by either template and buys nothing, while (ref_uri) is the only one DuckDB will index-scan — worth 122× on a selective lookup and a 1.6× penalty on everything else.

Template 1 — timeseries_info()

SELECT COUNT(*), MIN(ts), MAX(ts) … WHERE ref_uri = ?, run on the store’s write connection under its lock, exactly as main does. Every one of the 229 registered ref_uris, 10 repetitions each, per store. 226 of those 229 streams hold 443,790 rows apiece — so this sweep is overwhelmingly a test of the non-selective case, and there the (ref_uri) index is a pure tax.

Template 2 — timeseries()

The full generator from main: fresh DuckDB connection per call, WHERE ref_uri = ? plus optional ts bounds, ORDER BY ts, streamed to Arrow record batches with the value-mode logic applied. 20 query shapes × 100 reps × 3 stores; the iterator is drained every time. Latency tracks result size, not table size — until a stream is selective enough for an index scan to trigger.

no index idx (ref_uri) idx (ref_uri, ts)

One dense stream, windowed from 1 minute to its full range. Below ~1,000 rows every configuration flattens onto a ~3.6–4.6 ms floor that is not query work at all — it is the per-call duckdb.connect(), plan, and Arrow-reader setup that timeseries() pays on every invocation. Above ~10k rows latency is linear in rows returned, and the indexed stores are consistently slower because the scan they fall back to is the same one but their files are 4–8× larger.

Why: the plans

Taken from EXPLAIN ANALYZE on each store. Note that plain EXPLAIN reports a scan node in every case — only ANALYZE discloses Type: Index Scan, which is why the difference is invisible until you profile.

The composite index never appears in a plan. DuckDB’s ART index over (ref_uri, ts) is keyed on the concatenated tuple, so an equality predicate on the ref_uri prefix alone cannot drive a lookup — and both of main’s templates filter on exactly that. It is the most expensive configuration to build (52.2 B/row, 5.24 GB) and returns nothing for it. The (ref_uri) index does get used, and DuckDB’s optimizer correctly declines it once the predicate stops being selective.

Key findings

  • The composite (ref_uri, ts) index is dead weight for these two templates. It never appears in a query plan, measures within ±2% of no index on timeseries_info under interleaved control, and is the largest store on disk (5.24 GB, 52.2 B/row) and 10% slower to ingest. Every cost, no benefit.
  • (ref_uri) is the only index DuckDB will use here — and it is transformative exactly where it applies. A 3-row stream queried without a time bound goes from 194 ms to 1.59 ms (122×), and its timeseries_info from ~400 ms to 6 ms. Everywhere else it costs 1.2×–1.8×, because the fallback scan runs against a file 4× larger.
  • On this dataset the tax dominates the benefit, because 226 of 229 streams hold 443,790 rows each — the selective case is 3 streams. That ratio is a property of DPR SCADA data (every stream sampled at the same cadence), not of acquirium; a deployment with many short-lived or sparse streams would flip the verdict toward (ref_uri).
  • Bounded queries are cheap regardless of index. Anything up to a day of one stream (≤8,575 rows) answers in 3.6–10.6 ms in every configuration, and DuckDB’s zone maps prune the time range without help. Only unbounded full-stream reads reach the hundreds of milliseconds.
  • A ~3.6–4.6 ms floor sits under every timeseries() call and is pure per-call overhead — a fresh duckdb.connect() per invocation plus plan and Arrow-reader setup. For a 7-row query that is essentially the entire latency. Pooling or reusing read connections would cut small-query latency by roughly half, and unlike the index question it costs nothing in storage or ingest.
  • Empty results are correctly cheap (0.83–1.08 ms): the time-range predicate is pruned by zone maps before any data is touched.

Method. local_ingest_bench/query_bench.py. Three stores built from the same DPR CSVs to 100,296,256 rows each; every CSV is parsed, melted, assembled and value-split once and the resulting frame handed to all three stores, so only the store-specific DELETE+INSERT+COMMIT is repeated and no data is wasted. timeseries() and timeseries_info() are copied verbatim from git show main:src/acquirium/Storage/duckdb_store.py, including the fresh-connection-per-read, the streamed Arrow reader, the value-mode branching, and the write-connection lock on the aggregate. The 20 timeseries() specs are generated from the store’s own contents and every window is anchored on a timestamp taken by OFFSET from the target stream, so a gap in the SCADA record cannot silently produce an empty window; all 20 were executed and asserted before timing — 19 non-empty (3 → 443,790 rows), 1 deliberately empty. Caveats: single-threaded client, warm OS cache, one machine; the sequential sweep is order-sensitive at the ~15% level, which is why the timeseries_info comparison is repeated interleaved. Raw per-call data in results/query-bench/20260812-162825/results.json; the three stores are kept in local_ingest_bench/tmp_db/.
